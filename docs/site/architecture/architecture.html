Runtime architecture

How bkr combines the Boomkat C3 engine, uWebSockets, a thread-local runtime state, and a native worker pool.

Engine bridge and embedded JS layer

bkr compiles the Boomkat engine from source alongside runtime/*.c3 into a single executable. At boot, runtime/main.c3 creates a JsRuntime and JsContext, installs native callbacks on a hidden globalThis.__bk object, evaluates the embedded prelude (prelude.js, worker.js, fetch.js, websocket.js), and registers the built-in modules (http, net, file, process, path, permissions, typescript, crypto, test, repl, and optional sqlite).

Asynchronous operations cross the bridge through __bk.op(nativeFn, ...args) in runtime/bridge.c3. Each call allocates a monotonic 32-bit operation ID and a rooted JsDeferred promise capability in pending_ops. When the native operation finishes on the event loop, settle(id, ok, value, code) resolves or rejects the promise, drains the microtask queue, and flushes any unhandled promise rejections.

Event loop, thread pool, and resource table

Every execution thread owns a thread-local RuntimeState (g_runtime in runtime/state.c3) and a uSockets event loop (kqueue on macOS, epoll on Linux). Non-blocking TCP, TLS, HTTP, and timer events run directly on the uSockets loop. Blocking operations—filesystem calls, getaddrinfo DNS resolution, waitpid, Argon2id password hashing, and crypto.subtle EVP operations—are submitted to a shared 16-thread native pool (runtime/loop.c3) and post their completions back to the originating loop via uws_loop_defer.

Streamable OS handles (stdio, open files, TCP/TLS sockets, listeners, and child pipes) live in a per-runtime resource table (runtime/res.c3). Each resource ID (rid) packs a 12-bit generation counter above a 20-bit slot index so stale IDs after close() never alias recycled slots.

HTTP fast paths

runtime/http.c3 wraps uWebSockets via the C++ shim in shim/. Several paths avoid unnecessary JS allocations and VM transitions:

  • Static routes: Fixed buffered Response objects in serve({ routes, static }) are serialized into wire headers and body bytes at startup and answered directly from C3 without entering the VM.
  • Lazy requests and fast 200 responses: Incoming Request objects allocate a pre-shaped plain object; URL and header strings are materialized from the uWebSockets buffer only if read or if the request outlives the callback. Ordinary 200 responses with string, byte, or file.body() payloads serialize directly from C3.
  • Stream batching and file bodies: Untouched ReadableStream responses pull through a native sink in 64 KiB batches; streams that close within the first batch finish in one native uws_res_end call with a known content length. file.body(path) streams 64 KiB file chunks through the thread pool and pauses reads under socket backpressure.

Concurrency: module workers, HTTP workers, and HTTP processes

Boomkat VMs are single-threaded and share no mutable JS heap across threads:

  • Module workers (new Worker): Spawn a thread with a fresh g_runtime, VM, and uSockets loop. Messages encode value graphs into JSON metadata plus copied byte buffers.
  • HTTP workers (--http-workers=N): Spawn N - 1 sibling worker threads that re-execute the entry module and join the main server's acceptor pool; connections are dispatched round-robin.
  • HTTP processes (--http-processes=N): A native supervisor process binds the TCP port before any VM starts, forks N child processes, and distributes accepted socket file descriptors round-robin over Unix sockets using SCM_RIGHTS.
