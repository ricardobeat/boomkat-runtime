One native supervisor accepts connections and passes descriptors with SCM_RIGHTS.
Workers are spawned before VM initialization; HTTP/WebSocket bytes bypass the
supervisor. --http-processes=N creates N workers plus one supervisor.
The same new binary is used in every configuration; no old-binary comparison.

Functional validation: release and AddressSanitizer suites passed for independent
PIDs, distribution, bodies, streams, WebSockets, graceful HTTP/WebSocket drains,
bounded handoff queues, startup/bind/permission failures and crash cleanup.
Existing thread-pool, HTTP lifecycle, WebSocket and Worker regressions also passed.
The ASan check exposed and fixed stale HTTP pointers after WebSocket upgrade.

Machine: 8 CPU cores, 4 performance and 4 efficiency cores. Other workloads were
active. No builds or correctness tests ran concurrently with measured samples.
Every row below is the median of three fresh-process samples. RSS is the peak
summed RSS of the supervisor and all descendants, sampled every 100 ms; it is
not unique physical memory. Raw reports retain individual timings and host load.

HTTP: wrk, four client threads, 128 connections, 1s warmup + 5s measurement.
Variant and workload order rotate each round. The initial matrix had variable
p99s and slowing baselines, so the direct/2-process/4-process cases were rerun.

The hello-world baseline changed from 230,471 to 193,319 req/s between matrices;
its apparent scaling therefore is inconclusive. Async/echo gain throughput with
process pools in both matrices, but four-process p99 spikes persist. On this
loaded machine, two processes are the steadier latency/memory starting point.

CPU-bound handler: 10,000 synchronous integer-mixing iterations per request.
This isolates server parallelism from the high-rate loopback-client bottleneck.
wrk settings match HTTP above; this is a synthetic handler, not Taskboard.
workload      mode               req/s       p50 ms     p99 ms    tree RSS MiB
cpu           direct               4,190      30.620     32.070           12.91
cpu           processes-2          7,854      15.880     20.470           28.27
cpu           processes-4         12,423       9.990     15.730           54.41

Four-process CPU throughput is approximately 3x direct; this does not establish
a 10x improvement or a 2-million-requests/s frontend capacity.

Controlled connection churn: HTTP/1.1, 64 client goroutines on two Go scheduler
threads, at most 1,000 new connections/s; fresh destination port per sample.
One request per TCP connection, graceful close; 1s warmup + 3s measured. Every
status and exact body is checked, and connection count must equal successful
responses. No failures occurred in these bounded samples. This is a latency/
correctness check at a fixed rate, not a connection-capacity benchmark.
workload      mode               req/s       p50 ms     p99 ms    tree RSS MiB
hello         direct                 997       0.189      0.250           12.30
hello         processes-2            998       0.188      0.264           25.36
hello         processes-4            997       0.188      0.259           46.84

Rejected/screening churn attempts are retained and excluded from all tables:
- wrk with Connection: close reported read errors.
- ApacheBench HTTP/1.0 produced non-2xx responses.
- An unrestricted Go trial failed a warmup without retained client details.
- A graceful-close retry exhausted client ephemeral ports.
- A reset-after-response warmup recorded one EOF in 42,045 connections.
- A fresh-port reset trial exhausted kernel socket buffers in the direct baseline.
The EOF cause was not isolated. Unrestricted connection-churn reliability and
capacity remain unproven; do not infer production saturation limits from this
experiment. Partial reports and diagnostic traces are retained for review.

Reproduce HTTP repeat:
python3 bench/http-processes.py --rounds 3 --seconds 5 --connections 128 --client-threads 4 --processes 2,4 --threads 0 --report bench/http-processes-repeat.json

Reproduce CPU test:
python3 bench/http-processes.py --rounds 3 --seconds 5 --connections 128 --client-threads 4 --processes 2,4 --threads 0 --server bench/servers/process-cpu.js --workloads cpu --report bench/http-processes-cpu.json

Reproduce bounded connection churn:
python3 bench/http-processes.py --rounds 3 --seconds 3 --connections 64 --client-threads 2 --processes 2,4 --threads 0 --workloads hello --close-connections --churn-rate 1000 --report bench/http-processes-churn.json
