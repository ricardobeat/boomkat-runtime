HAProxy TCP comparison — 2026-10-31

Conclusion: HAProxy did not improve throughput over native FD dispatch on this Mac.
The fresh repeat confirms the direction on every workload. This is a same-host
comparison under variable background load, not a production capacity estimate.

Method
Same frozen bkr binary, route fixtures, HTTP/1.1 keep-alive, 128 connections,
wrk 2 client threads, 1s warmup then 5s measured. Three rounds per comparison,
rotating both route and case order, fresh services per sample. No runtime rebuild.
Direct = one bkr. dispatch-N = native supervisor plus N bkr workers.
haproxy-N-t1 = one HAProxy thread in TCP roundrobin mode plus N standalone bkr.
HAProxy forwards all traffic; native dispatch hands off FDs at connection setup.
HAProxy configured with maxconn 4096 and 5s connect / 30s client/server timeouts.
No TLS, HTTP parsing, health checks, or logging. Exact configs and argv in JSON.
bkr runs with --no-sandbox --no-prompt --allow-net=127.0.0.1 and bench read access.
Routes: hello=11-byte response, async=setImmediate then JSON, echo=1KiB POST,
cpu=10,000 synchronous JS integer-mixing iterations then JSON.

Checks
28 route/case correctness checks passed: exact status/body, repeated requests
on persistent connections, and HAProxy stats confirm all configured backends
have active connections. All 126 measured samples (6 screen + 84 main + 36 repeat)
and their warmups completed without wrk socket errors or non-2xx responses.
Binary hashes matched across all runs and were checked again after each run.

Interpretation and limitations
HAProxy frontend CPU is approximately one full core on the lightweight routes,
while the native supervisor is effectively idle after persistent connections
are assigned. The CPU-heavy workload spends most time in the JS backends, so
HAProxy overhead is proportionally smaller. These are measured associations,
not an isolated proof of which kernel or HAProxy operation limits throughput.
Native-dispatch wrk CPU approaches 200% on several lightweight routes: the
2-thread load generator can limit scaling. Four backends also compete with
wrk, HAProxy, and other applications on 4 performance + 4 efficiency cores.
Throughput and tail latency varied substantially between samples.
All samples are retained. The original direct echo run had p99 34.53ms;
other samples returned to normal. A whole fresh 3-round direct/4-backend
comparison was run for all routes, rather than deleting unfavorable samples.
No unrelated user processes were stopped. CPU and host load averages are in JSON.
No claim of linear scaling, connection-churn capacity, Linux performance, or
HAProxy production suitability follows from this keep-alive loopback benchmark.
