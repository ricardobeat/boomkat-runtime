paired measurements and latest full suite are in server-stream-native-results.txt.

A fresh server per runtime/case; 1s warm-up +2s measured; wrk -t2 -c128.
These ablations ran before the constant-check change, with the new engine caches.

Instruction counts use a separately built, non-threaded OP_PROFILE executable:
  c3c build bkr-perf-prof
  python3 bench/profile_stream.py ops
They count structural VM work, not CPU cost of the production threaded handlers.
Each case sends 1000 requests; the zero-request startup/stop count is subtracted.
The opcode diagnostics use the final constant-check code. Per extra chunk, the
1/8/64-chunk cases add about 71–72 instructions, 3 CALL opcodes, 15 LDREG register
copies, and 9 GETPROPC_CACHED reads. The 8-chunk path has about 41 CALL opcodes and
6 NEWARR instructions per request; a threaded CALL need not create a full frame.

The constant change removes global undefined lookups: 12,003 ->1,003 reads and
7,999 ->0 scope-cache head misses across 1000 requests. void 0 emits more cheap
instructions in this compiler, while eliminating the expensive name lookup.

Interpretation:
- Most of the fixed overhead is present before adding seven more chunks: a single
  chunk stream is much slower than a byte body. Stream/controller initialization,
  queue bookkeeping, the startup microtask and first pull are the major fixed path.
  This is an inference from ablations and code inspection, not per-function timing.
- Additional chunks add repeatable VM work in pull/enqueue/push, property reads,
  register copies and type checks. The VM/lookup sample share exceeds socket time.
- Batching all eight chunks in the first pull does not remove the startup queue:
  fetch invocation drains microtasks, so the initial pull runs through the normal
  controller before the HTTP direct pump takes over. It then transfers queued
  chunks into Sink. Changing microtask order would change observable behavior.
- The next larger lever is stream-state/controller initialization and the first
  queued pull, followed by reducing per-chunk interpreter work in Sink.enqueue.

comparisons. The direct-write case was about 83.5k req/s versus 27.4k for the

uses the direct-write API, so its gap includes differing stream abstractions.
Bun uses Web Streams in the published benchmark and is the closer API comparison.
