Native Request/Response fast-path experiment

Runtime baseline 4255e0c; engine 229e7b7a on both sides; matching O3 threaded builds. Candidate reverted under the requirement for general runtime gains. The final candidate reused two validated Request layouts and four guarded Response field layouts; it kept original metadata capture and spare body-request capacity.

Four alternating-order pairs per workload, fresh servers, 1s warm-up +3s measured, wrk -t2 -c128. Median per-run results. Latency and memory cells show baseline / candidate. Zero HTTP or socket errors.

Changing URL queries and request headers on every request: 187,714 -> 189,459 req/s (+0.9%), four alternating pairs. This remains too small to claim a broad improvement.

Discarded subexperiment: exact metadata reuse helped repeated requests but slowed changing-input requests by 1.2%; it was removed before final confirmation. The initial layout candidate also reduced body-request capacity from 8 to 5 slots, causing extra growth on body consumption and a 2.1% echo slowdown. Matching baseline capacity removed that slowdown.

Validation:
- Normal release HTTP suite and baseline-matched request/response mutation tests passed.
- Normal ASAN HTTP suite and mutation tests passed (leak detection disabled).
- Targeted mutation tests also passed with GC_STRESS, GC_VERIFY and POOL_BYPASS.
- Release retention stress: 5.9 MiB RSS growth over 1000 repeated stream/promise responses.
- Full forced-GC streaming retention stress aborts with GC_VERIFY incremental reachability mismatch on BOTH unchanged baseline and candidate; this is a pre-existing unresolved issue. Reproduce with c3c build bkr-perf-asan -D GC_STRESS -D GC_VERIFY -D POOL_BYPASS, then BKR_BIN="$PWD/out/bkr-perf-asan" BKR_HTTP_STRESS=1 ASAN_OPTIONS=detect_leaks=0 python3 tests/run_http.py.
